# seatly-api

Domain, orders, tickets and admin API for Seatly, an event ticketing platform with
real-time seat selection.

Owns users, venues, events, seats, orders, payments and tickets. Seat holds belong to
[seatly-realtime](https://github.com/tonixhaker/seatly-realtime) and are not stored here —
a seat in this database is `free` or `sold`.

## Stack

- PHP 8.4, Laravel 12
- PostgreSQL 17
- Sanctum for bearer-token auth
- RabbitMQ for publishing domain events
- Pest, Larastan level 9, Pint

## API

OpenAPI 3.1 in `docs/openapi.json`, generated by `dedoc/scramble`.
Event payload schemas in `docs/events/`.

## Running standalone

`seatly-api` expects three things around it, each at an environment variable:

| Dependency | Variables | Without it |
|---|---|---|
| PostgreSQL 17 | `DB_CONNECTION=pgsql`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` | only `GET /health/live` answers; `GET /health` returns 503 |
| RabbitMQ | `RABBITMQ_URL` | empty means domain events are validated and logged instead of published |
| [seatly-realtime](https://github.com/tonixhaker/seatly-realtime) | `REALTIME_URL`, `INTERNAL_TOKEN` | checkout cannot validate seat holds; the token must equal realtime's `INTERNAL_TOKEN` |

`APP_KEY` is always required. `.env.example` lists every variable with a local default.

A throwaway PostgreSQL matching those defaults — database, user and password all `seatly`:

```bash
docker run -d --name seatly-postgres -p 5432:5432 \
  -e POSTGRES_DB=seatly -e POSTGRES_USER=seatly -e POSTGRES_PASSWORD=seatly postgres:17
```

### With Docker

The image is self-contained: nginx and PHP-FPM, PostgreSQL driver included. It needs no
local PHP or Composer.

```bash
docker build -t seatly-api .
docker run --rm --name seatly-api -p 8000:8000 \
  -e APP_KEY=base64:$(openssl rand -base64 32) \
  -e DB_CONNECTION=pgsql -e DB_HOST=host.docker.internal -e DB_DATABASE=seatly \
  -e DB_USERNAME=seatly -e DB_PASSWORD=seatly \
  seatly-api
```

Serves on `http://localhost:8000`. `GET /health/live` answers without a database;
`GET /health` reports database readiness and returns 503 when Postgres is unreachable.
Create the schema and the demo data inside the running container with
`docker exec seatly-api php artisan migrate --seed --force`.

### Without Docker

Needs PHP 8.4 **with `ext-sockets`** and Composer. `php-amqplib` requires `ext-sockets`;
the Docker image builds it in, but a host PHP without it needs
`composer install --ignore-platform-req=ext-sockets`, which is also how any `composer`
command run in the stock `composer` image has to run, since that image does not ship the
extension.

```bash
composer install
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
php artisan serve
```

### Demo data

`php artisan db:seed` loads a browsable demo: two venues with different seat-map
geometries, two organizers, one buyer, and three events. Two are published with their seats
generated; the third stays a draft, which is what shows that the public catalog hides
unpublished events. The seeder prints the demo logins when it finishes.

The seeder is **idempotent, not destructive**: it deletes nothing, and a second run finds
the first organizer already present, prints `Demo data already present, nothing changed.`
and stops. To get fresh demo data, start from an empty database — remove the PostgreSQL
container and its data, start a new one, and run `php artisan migrate --seed` again. A run
interrupted part-way leaves the guard tripped over incomplete data and will not repair
itself — an empty database is the recovery from that too.

Seats are generated by publishing through the same `EventPublishService` an organizer's
`POST /organizer/events/{id}/publish` request uses, never by inserting `event_seats` rows
directly, so the demo data is data the application itself could have produced.

## Messaging

Domain events go to the topic exchange `seatly.events`, routed on the event type, in the
envelope frozen in `docs/events/envelope.json`. Every outgoing message is validated against
its own schema in `docs/events/` **before** the connection is opened: an envelope the
contract rejects is a producer bug and throws, while an unreachable broker is an
environment condition and is logged rather than raised — publishing must never take a
request down, and a missed message is repaired by the consumer's reconciliation path.

`EventPublisherInterface` binds to `RabbitMqEventPublisher` when `RABBITMQ_URL` is set and
to `LoggingEventPublisher` when it is empty. Both validate; the logging one is the
no-broker implementation, not a weaker path.

`REALTIME_URL` is where `seatly-api` reaches `seatly-realtime` for hold validation at
checkout, and `INTERNAL_TOKEN` is the shared secret for that call, both supplied as
environment variables. The token is sent as the `X-Internal-Token` header and never as a
query parameter, so it stays out of URLs, logs and exception messages.

## Tests

The Pest suite runs against a real PostgreSQL, not sqlite. `jsonb`, the database-level
enum `CHECK` constraints and the `gen_random_uuid()` primary-key defaults do not exist on
sqlite, so a suite pinned to it could not observe the schema it is meant to prove.
`phpunit.xml` forces `DB_CONNECTION=pgsql` and `DB_DATABASE=seatly_test`, and the test case
refuses to boot against any other database; a missing or unreachable database fails the run
loudly instead of skipping.

The suite drops and recreates every table in `seatly_test` on each run. Give it a
PostgreSQL of its own:

```bash
docker run -d --name seatly-postgres-test -p 5432:5432 \
  -e POSTGRES_DB=seatly_test -e POSTGRES_USER=seatly -e POSTGRES_PASSWORD=seatly postgres:17
```

With no local PHP, run it in an image built from this Dockerfile's `test` stage, which
carries the dev dependencies, with this checkout bind-mounted. The production image has no
dev dependencies and cannot run it:

```bash
docker build --target test -t seatly-api-test .
docker run --rm -v "$PWD":/var/www/html -v /var/www/html/vendor \
  -e APP_KEY=base64:$(openssl rand -base64 32) \
  -e DB_HOST=host.docker.internal -e DB_USERNAME=seatly -e DB_PASSWORD=seatly \
  seatly-api-test php artisan test
```

Do not pass `-e DB_DATABASE` — `phpunit.xml` pins it, and that is what keeps the wipe aimed
at `seatly_test`.

One test needs a live broker: `RabbitMqPublisherIntegrationTest` publishes a real message
and consumes it back to prove the routing key is the event type. It **skips** when
`RABBITMQ_TEST_URL` is unset. Start a broker and add the variable to the `docker run` above:

```bash
docker run -d --name seatly-rabbitmq -p 5672:5672 \
  -e RABBITMQ_DEFAULT_USER=seatly -e RABBITMQ_DEFAULT_PASS=seatly rabbitmq:3-management
```

```bash
-e RABBITMQ_TEST_URL=amqp://seatly:seatly@host.docker.internal:5672
```

CI sets the same variable against its own broker service, so the test is gated there rather
than only run by hand.

Six tests need a live `seatly-realtime`: `HoldsValidatorIntegrationTest` takes real holds
through `POST /holds` and checks them back through `GET /internal/holds/validate`, including
the different-session and different-event cases a stub cannot distinguish. They **skip**
when `REALTIME_TEST_URL` is unset; point it at a running realtime:

```bash
-e REALTIME_TEST_URL=http://host.docker.internal:3000
```

CI has no realtime service, so these six skip there; the timeout is covered unconditionally
by `tests/Unit/HttpHoldsValidatorTest.php` against a socket that never answers.

`phpunit.xml` forces `RABBITMQ_URL` empty and `REALTIME_URL` to `http://realtime.invalid`,
which keeps every other test on the logging publisher and on a faked HTTP client. Without
those forces, a developer whose `.env` points at a running broker or realtime would publish
real messages and make real validation calls during the suite while CI did not.

The unit suite is the other half of the contract: it must pass with **no database at
all**. `tests/Pest.php` binds `Tests\TestCase` to `Feature` only, so nothing under
`tests/Unit/` boots the application, and a domain service reached through a mocked
repository never opens a connection. Run it in an image that cannot open one — the stock
`php:8.4-cli` has no `pdo_pgsql` driver, while `phpunit.xml` forces `DB_CONNECTION=pgsql`:

```bash
docker run --rm -v "$PWD":/app -w /app php:8.4-cli vendor/bin/pest --testsuite=Unit
```

A unit test that reaches for the database fails there with `could not find driver` rather
than passing quietly against a connection it should never have had. CI enforces the same
thing with `DB_PORT=1`, since the runner does have the driver.
